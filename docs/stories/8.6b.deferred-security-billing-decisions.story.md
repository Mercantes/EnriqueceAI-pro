## 8.6b-1 — Dev Agent Record (D1+D2)

### Inventário (D1 — pré-requisito)
17 rotas sob `/api/admin` + `/api/workers`: **todas** já usam `verifyServiceRole`/`verifyCronSecret`, exceto `workers/backfill-kommo-won` (stub inerte 410, sem risco). Única chamada interna: `fetch-call-recording.ts` → `/api/workers/transcribe-call` com `Bearer service-role` → o gate permite. Nenhuma chamada cookie-based → default-deny seguro.

### Implementação
- **D1:** gate default-deny no `middleware.ts` para `/api/admin` e `/api/workers` — exige Bearer de service-role OU cron-secret (lista rotacionável) antes de chegar ao handler; senão 401. Prefixes removidos de `API_PUBLIC_PREFIXES`. Compare constant-time Edge-safe (sem `node:crypto`).
- **D2:** CSRF endurecido — mutação usa `Origin`, com fallback para `Referer`; sem nenhum dos dois (em rota cookie-based) → 403. **Reordenado**: gate privilegiado → skip cron/`crm/sync` (Bearer, sem CSRF) → públicas → CSRF. A ordem evita bloquear POST de cron (que não manda Origin).

- `src/middleware.test.ts` (novo — 8 testes: default-deny e CSRF)

## Scope (cada item = 1 decisão → 1 implementação)

### D1 — Middleware default-deny `/api/admin` + `/api/workers` (`src/middleware.ts`)
- Hoje: ambos os prefixes estão no allowlist público (bypass sessão+CSRF); proteção 100% delegada a cada handler chamar `verifyServiceRole`. Rota nova sem guard fica exposta.
- **Decisão necessária:** wrapper `withServiceRole()` por-rota vs. check no middleware.
- Pré-requisito: **inventariar todas as rotas** sob esses prefixes e confirmar que nenhuma legítima quebra.

### D2 — CSRF sem header `Origin` (`src/middleware.ts:~26`)
- Hoje: o check só roda `if (origin)`; mutação sem `Origin` passa.
- **Decisão:** fallback por `Referer` / negar mutações sem `Origin` em rotas sensíveis não-token.

### D3 — Ativação Stripe por `payment_status` (`src/app/api/webhooks/stripe/route.ts`)
- Hoje: `checkout.session.completed` ativa sem checar `payment_status` → boleto/PIX liberam acesso antes de compensar.
- **Decisão (adiada pelo usuário em ago/26):** gatear em `payment_status='paid'` + ativar pendentes via novo handler `invoice.payment_succeeded`. ⚠️ Sem o handler, gatear quebraria pagamentos assíncronos — os dois andam juntos.

### D4 — Enforcement server-side do SubscriptionGuard (`src/features/billing/components/SubscriptionGuard.tsx`)
- Hoje: bloqueio só client-side (contornável); `past_due` não bloqueia.
- **Decisão (adiada):** mover enforcement para o servidor (layout `(app)`/actions) + política de `past_due` (grace period?).
